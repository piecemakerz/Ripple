# 가설과 검증 기록

## X21 공개 전달 검증 — 2026-11-26

- D21과 사용자 명시 승인. 승인된 ZIP/영상 및 source manifest를 다시 hash 검사한 뒤 공개한다. 새 브랜치의 runtime/test/fixture는 검증본과 같아야 하며, 문서 갱신과 Git의 선언된 줄바꿈 정규화는 구분한다.
- 새 커밋에서 Verify Ripple 성공을 기다린다. PR은 draft로 유지하고 main을 병합하지 않는다. 릴리스는 공개 prerelease이며 승인된 ZIP/영상 및 해시·설명을 첨부한다.
- 인증 없는 릴리스/파일 접근, 다운로드 hash, 실제 영상 응답을 확인한다. 상태 문서·공개 URL·커밋과 릴리스 대상 대응을 기록하되 Devpost 접수나 독립 인간 검증으로 세지 않는다.

## X20 저장 안전성·원문 갱신·Ripple 자체 사례 — 2026-11-26

- **계획:** D20. 같은 revision을 읽은 두 클라이언트 중 오래된 저장은 409여야 하며 현재 결정·이력은 보존돼야 한다. 동일 request 재시도는 중복 이력을 만들지 않고, 수정된 요청 재사용은 거절해야 한다. 중간 실패·재시작·기존 저장소도 검사한다.
- **UI:** 실패/충돌에서 초안 유지, 최신 판단 확인 후 명시적 재저장, 변경 적용/원문/검토/다운로드/390px을 관찰한다. 원문 v2는 v1 인용과 snapshot을 바꾸지 않고 재검토 신호만 표시해야 한다.
- **사례·영상:** 변경 전 실제 코드·hash를 동결해 API→실행기→전달물 경로와 제외 작업을 설명한다. 준비 요청 수·자동 준비 시간과 수동 작성 범위를 기록한다. 영상 첫 결과는 30초 이내, 잘리지 않은 실제 화면과 다음 행동을 포함한다. 독립 인간 관찰이나 시간 절감으로 표현하지 않는다.
- **전달:** 전체 verify/doctor와 새 묶음 재현·hash 확인, 실제 공개 상태를 구분한다. 이전 후보는 덮어쓰지 않는다. 관측 결과는 실행 후 추가한다.

## X19 개선 후 수상 경쟁력 반증 검사 — 2026-11-26

- **연결:** D19. 이번 작업의 사전 계획이며 결과를 아래에 추가한다.
- **방법:** 공식 규정과 유사 제출물의 공개 설명/소스를 확인한다. 현재 화면에서 진입→영향/원문→판단→개인 문서 준비를 캡처하고 입력 부담·결과 의미·후속 행동을 조사한다. 현행 코드와 고정 SemVer 사례에서 그래프 탐색 정답과 업무적 필요성의 차이를 검토한다. 필요하면 임시 DB로 재현하며 live DB를 별도 프로세스로 열지 않는다.
- **판정:** 자격/접근, 작동성, 효용, 차별화, 데모 전달을 따로 평가한다. 확인 사실·추론·미검증과 실제 경쟁작 설명을 구분한 보고서를 만든다. 기존 84/84는 역사적 증거로 재사용하며 변경 없는 전체 회귀 실행을 새 검증으로 부풀리지 않는다.

### X19 관측 결과 — 2026-11-26

- **새 관측:** 현재 브라우저 8개 화면과 실제 8,275-byte brief 다운로드, 390px 리플로를 확인했다. 실제 영상의 첫 프레임을 새로 추출해 그래프 잘림을 확인했다. 독립 참가자는 여전히 0명이다.
- **반증 진단:** native in-memory API에서 표현만 바꾼 변경과 일정 변경이 동일한 5개 항목/7개 경로를 만들었다. 완전한 no-op는 거부됐다. 두 client가 같은 pending을 읽은 뒤 순차 저장하자 오래된 client의 판단이 최신 상태를 덮어썼고 이력 2개는 남았다. source v2 이후 v1 관계 근거와 경고 없는 영향 결과가 유지됐다. 실제 두 탭·사람 이해도 검사는 아니다.
- **기존 증거 재사용:** ZIP/영상 SHA 일치, runtime/검사/fixture/빌드 입력 108파일 일치. 같은 코드의 이전 84/84를 유지했고 전체 gate는 재실행하지 않았다. 실패한 최초 크기·로딩 캡처는 교체했고 cp949 helper 오류는 UTF-8로 재확인했다.
- **판정:** 기술적 재현성은 지지되지만 수상 충분성은 입증되지 않았다. 공개 전달, 입력 준비 대비 효용, 유사 출품작 대비 업무 가치, 데모 전달, 오래된 저장 보호가 남는다. [보고서](../HACKATHON_CRITICAL_REVIEW_2026-11-26.md)와 [QA](../QA.md)에 주장과 근거를 연결했다. 코드·후보 ZIP·영상·공개 저장소는 바꾸지 않았다.

## X18 최신 심사 요건·재현 패키지·실제 데모 — 2026-11-26

- **연결:** D18. 계획: URL로 SemVer 사례에 직접 진입, 적용 후 같은 검토 복원, 잘못된 링크의 명시적 실패, 다른 사례로 이동, 원문/검토 저장/모바일 회귀를 확인한다.

- **산출물:** 최신 공식 요건과 배점 평가, 실제 화면 기반 로컬 데모, 버전과 상태를 명시한 제출 안내. 로컬 생성·공개·접수·인간 검증은 각각 별개로 기록한다.
- **관측:** 실행 전 계획이다. 결과는 아래에 추가하며 과거 81-test 통과를 이번 검증으로 재사용하지 않는다.

### X18 관측 결과 — 2026-11-26

- **판정:** 로컬 구현·재현 기준을 충족했다. 공개 최신 소스/영상 접근·실제 접수는 미완료이며, 독립 사람 0명, 준비 시간·누락 감소·수상 성과는 미측정이다. 공개 전달을 완료하고 X05–X09의 실제 관찰을 다음으로 유지한다. 개발자가 사례를 성공한 결과를 인간 효용으로 일반화하지 않는다.

## 앞으로 검증할 제품 가설

아래 기준은 학습을 위한 소규모 제안이다. 실제 실행 전 대상·조건·판정 기준을 확정하고 변경 이유를 기록한다. 적은 참가자의 관찰을 모집단 성공률이나 통계적 개선으로 일반화하지 않는다. 실행·모집·메시지 발송은 이번 기록 작업의 범위가 아니다.

### X05 문제 자체가 실제로 중요한가

- 관련 결정: D01. 상태: 미실행.
- 방법: 대상 역할 3명을 우선 관찰·인터뷰한다. 제품을 설명하기 전에 최근 요구사항 변경 사례, 놓친 후속 작업, 현재 해결 방식, 발생 빈도와 비용을 묻는다. 최근 사례의 시점도 남긴다.
- 제안 기준: 3명 중 2명 이상에게서 구체적인 최근 사례와 현재 방식의 불편을 확인하면 다음 실험으로 진행한다. 그렇지 않으면 대상 역할·문제를 다시 좁힌다. 호의적인 반응만으로 통과시키지 않는다.
- 원자료: 익명 ID, 모집 경로·사전 친분, 실제 발언과 관찰, 반례, 반복 사용 의향의 이유. 시간·금액은 응답자의 추정인지 직접 측정인지 구분한다.

### X06 샘플을 마치고 이유를 설명할 수 있는가

- 관련 결정: D06·D07·D09. 상태: 미실행.
- 방법: 처음 보는 사람 3명에게 선호 언어로 샘플을 제공하고 도움 없이 시작하도록 한다. 첫 행동, 멈춘 지점, 필요한 도움, 완료 시각을 기록한다. 완료 후 직접·간접 영향 한 개씩의 근거, T3 제외 이유, Defer와 구현 완료의 차이를 설명하게 한다.
- 제안 기준: 2명 이상이 개입 없이 완료하고 위 개념을 설명할 수 있어야 다음 흐름으로 진행한다. 버튼을 누른 횟수와 원문을 연 사실만으로 이해를 판정하지 않는다.
- 실패 시: 가장 먼저 반복해서 막힌 개념·화면 한 곳부터 수정하고 새 참가자로 확인한다. 같은 사람의 재시도는 학습 효과가 포함된다고 기록한다.

### X07 개인 문서로 첫 검토까지 갈 수 있는가

- 관련 결정: D03·D08·D09. 상태: 미실행.
- 방법: 공개 가능한 익숙한 문서 또는 동의받은 비식별 자료로 원문 → 항목 2개 → 관계 → 변경 → 첫 검토를 수행한다. 샘플 경험 유무와 문서 친숙도를 기록한다.
- 제안 기준: 준비 비용과 막힌 이유를 모두 기록하고, 도움 없이 첫 저장에 도달하며 사용자가 관계 방향·인용 근거를 설명할 수 있어야 한다. 첫 관찰에서 시간 분포를 얻기 전 임의의 시간 절감 목표를 만들지 않는다.

### X08 준비 비용을 포함해 현재 방식보다 나은가

- 관련 결정: D01·D03·D04·D06. 상태: 미실행.
- 방법: [기존 비교 프로토콜](../SEMANTIC_REVIEW.md)의 정답 의미 검토·순서 교차·동일 정보 조건을 따른다. 원문 검색 방식과 Ripple을 비교하고, 이미 답을 본 사람은 독립 참가자로 취급하지 않는다.
- 지표: 놓친 항목·잘못 추가한 항목·근거 오류·완료 시간. 문서 입력·관계 확인·교육·갱신 비용을 따로 남긴다. `총비용 = 준비 + 교육 + 변경별 검토 + 관계 유지`로 정의하고 실제 관측된 변경 횟수만 사용한다.
- 제안 기준: 더 적은 누락·잘못된 경고 또는 더 빠른 근거 있는 검토가 관찰되더라도 준비 비용을 함께 보고한다. 결과가 엇갈리면 보류한다. 두 사례만으로 보편적인 우위를 주장하지 않는다.
- 실패 시: 추출·관계 품질, 준비 부담, 검토 UI, 과제 난이도를 구분해 다음 실험 하나를 선택한다. 효과 크기·손익분기점은 데이터 없이 채우지 않는다.

### X09 짧은 데모가 문제와 차이를 전달하는가

- 관련 결정: D04·D06. 상태: 미실행.
- 방법: 완성된 2분 이내 영상 또는 실제 리허설을 처음 보는 3명에게 보여주고 제품 설명을 다시 말하게 한다. 문제·Relate의 역할·근거가 있는 영향·저장된 결정의 의미·기존 방식과의 차이를 확인한다.
- 제안 기준: 2명 이상이 핵심을 설명하고, AI 자동 추출이나 구현 자동 완료로 오인하지 않아야 한다. 실행 가능성은 별도로 로그인 없는 재생과 깨끗한 환경의 실행으로 확인한다.
