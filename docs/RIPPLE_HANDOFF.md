# Ripple 프로젝트 개발 인수인계

작성일: 2026년 11월 12일 KST

공개본 안내: 개인 PC 경로 두 곳만 익명화했다. 아래 내용은 구현 전의 원래 계획이며, 현재 상태는 `STATUS.md`와 `HACKATHON_AUDIT.md`를 따른다.

Ripple은 요구사항이나 전제가 바뀌었을 때 다시 검토할 결정과 작업을 찾고, 그 이유를 원문과 의존 경로로 보여주는 도구다. Relate by Neo4j Hackathon 제출을 목표로 한다. 이 문서를 읽은 개발 세션은 기존 대화 없이 프로젝트 세팅부터 시작할 수 있다.

현재 완료된 것은 아이디어 선정과 이 인수인계 문서다. Ripple 코드, 패키지 설치, Relate 연동, 실행 및 테스트는 아직 수행하지 않았다. 아래 기술 구성과 데이터 모델은 구현을 위한 기본안이며, 실제 환경에서 검증한 뒤 필요한 부분을 조정한다.

## 새 세션의 시작 지시문

다음 내용을 새 세션에 전달하면 된다.

> 이 문서를 읽고 Ripple 프로젝트의 로컬 개발 환경 세팅부터 진행해주세요. 기존 파일과 프로젝트 지침을 먼저 확인하고, Ripple 전용 디렉터리에서 작업하세요. 첫 목표는 실제 Relate에 샘플 의존 관계를 저장하고, 변경 영향 경로를 조회하고, 프로세스를 재시작해도 데이터가 유지되는 것을 검증하는 것입니다. 이어서 작은 화면에서 변경 선택, 영향 목록, 원문 근거 확인까지 연결해주세요. AI API 키가 없어도 샘플 그래프로 진행하세요. 합리적인 기술 선택은 근거를 기록하며 진행하고, 실행한 명령·검증 결과·남은 문제를 보고해주세요.

이 지시문의 첫 작업 범위는 아래 M0와 M1이다. 이후 단계도 전체 개발 방향으로 참고하되, 단계별로 실행 가능한 결과를 남긴다.

## 사용자와 작업 환경

사용자는 프론트엔드 개발 경력 5년이며 백엔드 관련 지식이 있다. 혼자 참여하고 전체 구현을 AI에 맡길 계획이다. 사용자에게 중요한 역할은 제품 판단, 도메인 사례 확인, 사용성 검토다. 주당 투입 시간, API 예산, 실제 사용자 사례는 아직 정해지지 않았다.

| 항목 | 기본값 |
| --- | --- |
| 인수인계 당시 작업 폴더 | `<original-workspace>` (개인 PC 경로 생략) |
| 인수인계 당시 문서 | `<original-workspace>/RIPPLE_HANDOFF.md` |
| Ripple 구현 위치 | 위 작업 폴더 아래 `ripple` 디렉터리 |

| 기본 실행 형태 | 로컬 단일 사용자 웹앱 |

현재 작업 폴더에는 `.git`과 다른 프로젝트·자료가 있다. 기존 내용을 보존하고 Ripple 변경만 분리한다. 작업을 시작할 때 적용되는 `AGENTS.md`, Git 상태, 기존 `ripple` 존재 여부를 확인한다. 새 저장소가 필요해도 상위 저장소 전체를 Ripple 저장소로 취급하지 않는다. 공개 제출 범위는 Ripple 코드와 공개 가능한 샘플로 제한한다.

사용자는 현재 문서 작성을 요청했으며 이 세션에서 구현은 시작하지 않았다. 새 세션에서 위 시작 지시문을 받으면 로컬 세팅과 개발을 진행한다.

## 제품 문제와 대표 사용자

대표 사용자는 작은 제품팀의 PM, 프론트엔드 개발자, 기술 리드다. 요구사항과 회의록에 흩어진 전제가 바뀌었을 때, 그 전제를 바탕으로 이미 결정한 기능과 배정한 작업을 다시 찾는 상황을 해결한다.

제품의 핵심 질문은 다음과 같다.

> 이 전제가 바뀌면 어떤 결정과 작업을 다시 검토해야 하며, 그렇게 판단한 근거는 무엇인가?

Ripple은 관계를 근거로 재검토 대상을 제시한다. 연결된 작업이 잘못됐다고 자동 판정하거나 업무를 자동 수정하지 않는다. 최종 결정은 사용자가 유지, 수정, 보류로 기록한다.

시간에 따른 사실 관리와 출처 보존 자체는 [Graphiti](https://github.com/getzep/graphiti) 같은 기존 프로젝트에서도 다룬다. Ripple의 차별화 목표는 제품팀이 변경을 발견하고 영향의 근거를 확인한 다음 검토를 마치는 사용 흐름이다.

## 첫 데모 시나리오

초기에는 가상의 재고 관리 제품을 사용한다. 실제 사용자 사례가 확보되면 같은 구조로 교체할 수 있다. 합성 자료임을 README와 데모 데이터 안내에 표시한다.

| ID | 종류 | 내용 |
| --- | --- | --- |
| A1 | 전제 | 공급업체 API는 재고를 실시간으로 갱신한다 |
| D1 | 결정 | 제품 화면에 실시간 재고 배지를 표시한다 |
| D2 | 결정 | 재고 변화에 따라 품절 알림을 제공한다 |
| T1 | 작업 | 재고 배지 UI 구현 |
| T2 | 작업 | 품절 알림 조건 구현 |
| T3 | 작업 | 비밀번호 재설정 화면 구현 |

확인된 의존 관계는 `D1 → A1`, `D2 → A1`, `T1 → D1`, `T2 → D2`다. 화살표는 항상 **왼쪽 항목이 오른쪽 항목에 의존함**을 뜻한다. T3는 이 변경과 관련이 없다. 각 의존 관계에는 이를 설명하는 회의록 또는 요구사항 문장을 준비한다.

새 API 문서에서 갱신 주기가 하루 한 번이라고 설명한다. 사용자가 이 변경을 A1의 수정으로 확인하면, D1·D2와 T1·T2를 재검토 대상으로 제시한다. T3는 경고하지 않는다. 예를 들어 T1의 근거 경로는 `T1 → D1 → A1`이며 각 연결을 클릭해 원문을 읽을 수 있어야 한다.

데모 흐름은 다음과 같다.

1. 기존 요구사항과 작업을 연다.
2. 새 문서의 갱신 주기를 확인하고 A1 변경을 적용한다.
3. 영향을 받는 결정과 작업이 표시된다.
4. T1을 선택해 경로와 근거 문장을 확인한다.
5. 검토 결과와 이유를 기록한다.
6. 앱을 재시작해 그래프와 검토 기록이 남아 있음을 확인한다.

## 한 달 MVP 범위

아래 다섯 기능을 제출 버전의 범위로 삼는다.

| 기능 | 구현할 행동 | 완료 기준 |
| --- | --- | --- |
| 문서 입력 | Markdown·일반 텍스트 붙여넣기 또는 업로드 | 원문과 문서 버전 보존 |
| 관계 제안과 확인 | AI 추출 결과를 검토하고 관계 확인·거절·수정 | 확인된 관계와 미확인 제안 구분 |
| 변경 영향 탐색 | 사용자가 특정 전제의 변경을 확인 | 실제 Relate 질의로 직접·간접 영향 반환 |
| 근거 탐색 | 영향 항목에서 경로와 원문 열기 | 각 의존 관계의 출처 확인 가능 |
| 검토 처리 | 유지·수정·보류와 이유 저장 | 변경 건별 상태와 이력이 재시작 후 유지 |

첫 구현은 문서와 전제를 사용자가 명시적으로 연결하는 방식으로 충분하다. 임의의 두 문서에서 모든 모순을 자동 탐지하는 기능은 확장 과제다. 사용자 확인을 거친 소규모 그래프로 핵심 흐름을 먼저 완성하고 AI 추출을 붙인다.

초기 범위에 계정·조직 관리, 실시간 다중 사용자 협업, Slack·Jira·Notion 동기화, 웹 전체 수집, PDF OCR, 모바일 앱, 자동 코드 수정, 다중 에이전트 실행 플랫폼은 포함하지 않는다. 검색·벡터 임베딩·MCP 연동도 핵심 흐름이 완성된 뒤 판단한다.

## 기술 구성과 세팅 순서

기본안은 React·TypeScript·Vite 프론트엔드와 작은 Node.js·TypeScript 백엔드다. 그래프 화면에는 React Flow 같은 라이브러리를 검토할 수 있다. 구체적인 프레임워크와 버전은 새 세션에서 호환성을 확인하고 고정한다. 기존에 Ripple 코드가 생겼다면 그 구성을 우선 존중한다.

권장 데이터 흐름은 다음과 같다.

```text
React 화면
   → 로컬 API와 입력 검증
      → 변경 및 검토 서비스
         → Relate 저장소 어댑터
            → 디스크의 Relate 데이터

문서 추출 서비스 → 구조화된 관계 제안 → 사용자 확인 → Relate 기록
```

핵심 항목, 의존 관계, 출처, 변경·검토 이력은 Relate에 저장한다. JSON 파일은 샘플 입력·평가 정답·내보내기에 사용한다. 영향 결과는 실행 중인 Relate에서 조회한다.

Relate 공식 저장소는 Node, Python, CLI와 영구 저장 방식을 안내한다. 다만 패키지 배포 진행에 관한 주의사항도 있으므로 npm 설치가 된다고 가정하지 않는다. [Relate 공식 저장소](https://github.com/relatedb/relate)

새 세션의 세팅 순서는 다음과 같다.

1. Node, 패키지 매니저, Git, 필요한 런타임 버전을 확인한다.
2. 공식 설치 안내와 릴리스를 읽고 현재 OS에서 사용 가능한 배포를 확인한다.
3. Node 바인딩으로 열기·쓰기·질의·닫기·재열기를 검증한다.
4. Node 배포가 막히면 공식 Python 배포 또는 로컬 Relate 서버 인터페이스 중 실제 실행 가능한 하나로 백엔드를 조정한다. 선택 이유와 설치 절차를 남긴다.
5. 실제 설치된 버전에서 영구 저장, 매개변수 질의, 여러 단계 경로 탐색, 트랜잭션 동작을 검증한다.
6. 검증이 끝난 버전과 패키지 잠금 파일을 기록한 뒤 UI와 연결한다.

Relate는 단일 프로세스 중심의 엔진이다. MVP에서는 하나의 백엔드가 저장소를 소유하고 쓰기를 순차 처리하도록 한다. 네이티브 DB와 디스크 저장을 지원하는 실행 방식을 먼저 확보한다. [공식 제약사항](https://github.com/relatedb/relate/blob/main/docs/limitations.md)

현재 작업 경로는 OneDrive 아래다. 활성 DB의 위치는 설정으로 분리하고, 동기화 잠금 문제가 나타나면 로컬 데이터 폴더로 옮긴다. 제출용 저장소는 DB를 정상 종료한 후 일관된 상태로 복사하고 다시 열어 검증한다.

## 최소 데이터 모델

다음은 구현 시작점이다. 필요한 세부 필드는 테스트를 통해 정하되 관계 방향과 출처 추적은 유지한다.

| 개체 | 주요 필드와 역할 |
| --- | --- |
| Item | 안정적인 ID, 종류 Assumption·Decision·Task, 제목, 내용, 현재 revision |
| Person | 담당자 ID와 표시 이름 |
| SourceVersion | 문서 ID, 버전 ID, 제목, 변경되지 않는 원문, 해시 |
| Evidence | 원문 버전 ID, 정확한 인용 구간과 인용문 |
| Change | 변경 ID, 대상 Item ID, 변경 전후 내용·revision, 확인 시각 |
| Review | Change와 영향 Item의 조합, 검토 상태, 이유, 영향 경로 스냅샷 |

주요 관계는 다음과 같다.

```text
(downstream:Item)-[:DEPENDS_ON]->(upstream:Item)
(task:Item)-[:OWNED_BY]->(person:Person)
(item:Item)-[:EVIDENCED_BY]->(evidence:Evidence)
(evidence:Evidence)-[:FROM_SOURCE]->(source:SourceVersion)
(change:Change)-[:CHANGES]->(item:Item)
(review:Review)-[:FOR_CHANGE]->(change:Change)
(review:Review)-[:FOR_ITEM]->(item:Item)
```

`DEPENDS_ON` 관계에도 안정적인 관계 ID, 확인 상태, 근거가 되는 Evidence ID를 저장한다. 항목의 내용에 대한 출처와 항목 사이의 의존 관계에 대한 출처를 구분한다.

관계 상태는 proposed, confirmed, rejected, superseded를 기본으로 하며, 영향 계산에는 confirmed만 사용한다. 화면에는 사용자가 이해할 수 있는 이름으로 표시한다.

Evidence는 변경되지 않는 SourceVersion의 원문을 참조한다. 문자 위치를 세는 방식을 통일하고, 저장할 때 인용문과 대상 구간이 일치하는지 검증한다. 근거가 없는 관계는 근거가 확인된 관계로 취급하지 않는다.

변경을 적용하기 전에 기존 확인된 그래프에서 영향과 근거 경로를 구한다. 그 결과를 Change와 Review에 연결해 저장하고 대상 내용을 갱신한다. 이후 관계를 편집해도 과거 검토에서 제시한 경로와 원문 버전을 추적할 수 있어야 한다. 저장 도중 실패해서 변경만 적용되는 상황을 막도록, 실제 환경에서 검증한 트랜잭션 또는 복구 가능한 갱신 절차를 사용한다.

## 영향 계산 규칙

변경된 항목에서 확인된 `DEPENDS_ON` 관계를 역방향으로 따라가며 의존하는 항목을 찾는다. 위 예시에서는 A1에서 D1과 D2, 이어서 T1과 T2에 도달한다. 담당자가 같거나 공통 키워드가 있다는 이유로 영향을 확장하지 않는다.

- 직접 영향과 간접 영향을 구분하고 근거 경로를 반환한다.
- 여러 경로가 같은 작업에 도달해도 목록과 Review를 중복 생성하지 않는다.
- 순환 관계에서도 탐색이 종료되며, 변경 대상 자체를 의존 항목으로 다시 표시하지 않는다.
- 탐색 깊이나 반환 건수를 제한했다면 결과가 일부 생략됐음을 표시한다.
- 변경마다 Review를 분리하고, 이전 변경의 검토 상태를 새 변경에 그대로 적용하지 않는다.
- 유지는 이번 변경에 대한 판단으로 저장한다. 의존 관계를 자동 삭제하지 않는다.
- 수정은 대응 방침의 기록을 뜻한다. 실제 구현 작업까지 완료됐다고 표시하지 않는다.
- 같은 요청을 다시 보내도 Change와 Review가 중복 생성되지 않도록 한다.

이 규칙을 만족하는 Cypher와 API는 설치된 Relate의 명세로 검증해 구현한다. 통합 테스트에서는 화면용 모의 데이터가 아니라 실제 DB가 반환한 결과를 확인한다.

## AI가 담당하는 처리

AI의 주요 역할은 문서에서 후보를 추출하고 저장된 근거를 설명하는 것이다. 모델의 출력은 Item 후보, 의존 관계 후보, 출처 구간 등으로 구조를 제한한다. 서버에서 ID, 참조 대상, 인용문, 종류를 검증한 뒤 제안으로 저장한다.

영향 대상은 확인된 관계를 탐색해 결정한다. 설명문에는 실제 반환된 경로와 Evidence를 사용한다. 출처 없는 의존 관계나 근거를 설명에 추가하지 않는다. 입력 문서에 포함된 명령은 실행 지시가 아닌 문서 내용으로 다룬다.

API 키와 모델은 미정이다. 처음에는 샘플과 수동 편집으로 진행한다. 추출 서비스는 교체 가능하게 구성하고, 외부 모델을 호출할 때 이용 가능한 서비스와 예산을 확인한다. 비밀 정보는 서버 환경변수로 관리하고 저장소나 브라우저 배포물에 포함하지 않는다.

데모에는 키 없이 열 수 있는 샘플 모드를 제공한다. 샘플 문서와 관계 후보를 함께 제공하되 영향 탐색, 편집, 저장은 실제 Relate로 실행한다. 고정된 추출 예시를 실시간 AI 생성 결과로 설명하지 않는다. 임의 문서에 대한 추출은 키를 설정한 모드에서 별도로 검증한다.

## 화면 구성

데스크톱에서는 왼쪽에 원문과 변경 내용, 가운데에 선택한 영향 경로, 오른쪽에 영향 목록과 검토 기능을 배치한다. 노드 종류, 변경 대상, 확인 상태를 문자로도 식별할 수 있게 한다.

첫 화면에서 샘플을 열고 변경 하나를 선택해 영향을 확인할 수 있어야 한다. 사용자가 이해해야 할 것은 변경 내용, 영향 대상, 근거, 다음 판단이다. DB 내부 정보는 개발자용 상세 영역에 모은다.

빈 상태, 로딩, 추출 후보 확인, 영향 없음, 근거 부족, 저장 실패, 재시도, 일부 결과, 검토 완료 상태를 설계한다. 오류가 나도 입력을 보존한다. 작은 화면에서는 패널 전환을 지원하는 정도로 대응한다.

## 구현 마일스톤

기간은 예상치이며 사용자가 확약한 투입 시간이 아니다. 각 단계는 실행되는 결과로 완료 여부를 판단한다.

| 단계 | 예상 기간 | 결과물과 완료 조건 |
| --- | --- | --- |
| M0 | 첫 1~2일 | 설치 절차와 실DB 검증. 저장, 경로 탐색, 재시작 복원 성공 |
| M1 | 1주 차 | A1 변경에서 D1·D2·T1·T2와 근거를 표시. T3는 제외 |
| M2 | 2주 차 | 문서 입력, AI 후보, 관계 확인, 변경 적용이 이어서 동작 |
| M3 | 3주 차 | 검토 상태와 이력, 화면 개선, 평가 사례, 사용자 확인 |
| M4 | 4주 차 | 오류 수정, 새 환경에서 재현, README, 영상과 제출 설명 |

M0에서는 빈 DB에 대표 시나리오를 저장하고, 동일한 의존 탐색으로 직접 영향과 간접 영향을 구하고, 프로세스를 종료한 후에도 결과가 일치하는지 확인한다. 성공 로그와 버전을 남긴다.

M1에서 추출용 외부 API는 필수가 아니다. 핵심 기능의 구현 순서는 데이터 저장, 영향 계산, 근거 표시, 검토 저장, AI 추출, 화면 조정이다.

## 평가와 완료 기준

대표 시나리오의 정답을 먼저 고정하고 이후 약 20개 사례로 확장한다. AI가 사례와 정답 초안을 작성할 수 있다. 사람이 확인한 사례와 확인 전인 합성 사례를 기록에서 구분한다.

평가는 두 가지로 나눈다. 확인된 그래프의 영향 탐색에서는 기대한 영향 집합과 경로가 나오는지 본다. 문서 추출에서는 후보의 적절성, 인용 정확성, 사람이 수정한 양을 본다. 추출 실패와 탐색 실패를 구분한다.

평가 사례에는 직접 의존, 여러 단계, 무관한 작업, 같은 담당자, 같은 단어, 미확인 관계, 거절된 관계, 순환, 여러 경로, 두 번째 변경, 중복 요청, 근거 누락, 원문 버전 보존, 재시작 복원을 포함한다.

평가 지표는 다음을 사용한다.

- 적합률: 반환한 영향 항목 중 정답에 포함된 비율.
- 재현율: 정답 영향 항목 중 발견한 비율.
- 근거 정확성: 관계의 출처가 존재하고 인용문이 원문과 일치하는지.
- 사용자 테스트: 영향과 이유를 찾는 시간, 놓친 항목, 이해하기 어려웠던 부분.

고정 그래프의 회귀 테스트는 기대 집합과 완전히 일치하는 것을 목표로 한다. 임의 문서의 정확도나 시간 단축은 측정한 실제 값만 보고하고, 합성 데이터의 성적을 실제 사용에서의 보장으로 표현하지 않는다. 비교 실험은 같은 자료와 과제로 진행한다.

기술 검증은 타입 검사, 빌드, 영향 계산 테스트, 실제 Relate 영구 저장 테스트, 대표 흐름의 E2E를 중심으로 한다. 주요 화면을 실제로 열어 원문, 경로, 조작 요소의 가독성도 확인한다.

## 제출 가능한 상태

- 새로운 환경에서 README 절차에 따라 실행할 수 있다.
- API 키 없이 샘플의 핵심 기능을 사용해 볼 수 있다.
- 키를 사용하는 AI 추출의 설정과 실행 조건을 명시한다.
- 수정한 그래프와 검토 기록이 재시작 후에도 유지된다.
- 공개 가능한 샘플 문서, 평가 사례, 정상적으로 열리는 Relate 저장 데이터가 있다.
- README에 대상 사용자, Relate 사용 이유, 저장 형식, 데이터 위치, 제약, 실행과 평가 절차가 있다.
- 1~2분 영상이 변경부터 근거 확인과 검토까지 보여준다.
- 평가 수치, 사용자 의견, 기능 설명이 실제 결과와 일치한다.

내부 완성 목표는 제출 마감 이틀 전으로 잡고, 남은 시간은 재현 확인과 제출에 사용한다.

## 사용자와 AI의 분담

| 작업 | 사용자 | 개발 AI |
| --- | --- | --- |
| 문제 설정 | 실제 변경 사고나 불편 설명 | 요구사항과 대상 범위 정리 |
| 샘플 | 의존 관계의 의미 확인 | 문서, 그래프, 평가 사례 작성 |
| 개발 | 제품을 사용하고 피드백 | 세팅, 설계, 구현, 테스트, 수정 |
| 사용성 확인 | 개발자나 PM에게 협조 요청과 사용 관찰 | 과제, 질문, 기록 형식, 결과 정리 |
| 제출 | 본인의 참가 정보와 최종 설명 확인 | README, 데모 대본, 제출문 초안 |

실제 사례나 협력자가 없어도 합성 시나리오로 M0와 M1을 진행할 수 있다. 사용 서비스, 예산, 실제 자료의 사용 가능 여부 등은 작업 판단에 필요한 시점에 짧게 확인한다.

## 다음 세션에 남길 기록

구현을 시작하면 Ripple 디렉터리 안에 `README.md`와 `docs/STATUS.md`를 만든다. 실제 동작한 실행 명령, 채택한 버전, 저장 위치, 확인된 기능, 최근 검증 결과, 남은 문제, 다음 작업을 기록한다. 아직 구현하지 않은 명령을 실행 가능한 절차로 안내하지 않는다.

이 문서는 명세의 출발점으로 보존하고 변경한 판단에는 이유를 남긴다. 첫 완료 보고에는 M0 검증 결과, 실행 방법, M1에서 완성한 기능, 사용자가 확인할 구체적인 부분을 포함한다.
