## Review revisions, request receipts and source freshness — 2026-11-26

D20 addresses the preceding D19 findings. Every review write carries an expected revision and UUID request identity. The fingerprint includes operation, change, item and input. A transaction validates the revision, updates the review, appends an immutable event and saves a Mutation receipt. Exact retries return the current detail without replaying the write; reused IDs with different input and stale revisions are 409 errors. Content-identical fresh requests may create a receipt without another revision/event. The one-process synchronous mutation boundary remains. Legacy reviews derive revision from preserved event count, avoiding a history rewrite. Review receipts alone do not classify the built-in workspace as imported context.

The UI captures the read revision in the draft. Background refresh must not silently advance that baseline. Conflict handling preserves the draft, retrieves the latest decision, blocks save and offers explicit comparison choices. Retry identity remains stable for the same payload; changing payload/baseline creates a new ID. Generic network failure preserves the draft. No multi-user service or runtime model was introduced.

Source freshness compares numeric versions within the same document, bounded by the import source cap. Original evidence and saved path snapshots remain immutable. Current workspace sources and evidence details supply an optional newer document; this is a nonblocking re-review signal, not automatic relationship invalidation. Named sample versions are not ordered. Document title prefill applies only to an empty draft title.

The real Ripple API-change fixture uses six frozen pre-change working-tree excerpts with null commit provenance, exact hashes and UTF-16 ranges. Its four manually confirmed connections include the indirect bundle→worker→API consequence. `runPhase` provides explicit intermediate invocation evidence. It is developer-authored regression context, not an automatically discovered code graph or human efficacy result. Judge bundles now identify the selected case; bundles lacking that field retain the prior SemVer default. Sources and closed native snapshots are hashed, while launch and read-only inspection use separate copies. [Case](RIPPLE_CHANGE_CASE.md), [results](HACKATHON_IMPROVEMENTS_2026-11-26.md).

## Critical review: interpretation and stale writes — 2026-11-26

D19/X19 added evidence without changing code. Native/API probes confirmed that `impact(id)` depends on confirmed graph topology; editorial and schedule changes to the same item yield the same candidate set. Exact no-op text is rejected. Preserve the distinction between reachable review candidates and automatically inferred failures or required edits; immutable quote validation does not establish business meaning.

Review updates currently accept only status/reason. They serialize transaction execution but do not compare the review state a client previously read. A stale client can overwrite the current decision; immutable ReviewEvents retain both decisions. A future fix should add a review revision/precondition, explicit conflict recovery and idempotency semantics without weakening history. No fix was made during the reassessment.

Saving a newer source version preserves old evidence and does not invalidate/review existing items or relationships automatically. A future source-freshness signal must remain distinct from declaring a confirmed relation false. [Critical report](HACKATHON_CRITICAL_REVIEW_2026-11-26.md) supplies observations, priorities and acceptance criteria.

## Judge entry and inspectable bundles — 2026-11-26

Each start creates a distinct directory; restarting ongoing work must reuse the printed working DB path. These checks use synthetic fixtures, not live-store export or human validation. No schema, production query, dependency or model setting changed.

## Boundaries

Development learning is stored separately in [docs/learning](learning/README.md): dated decision summaries, evidence provenance, experiments and outcome review. Historical entries are explicitly reconstructed from existing documents; future entries preserve prior predictions and append outcomes. This is a repository documentation convention, not a product feature, Relate schema change, automatic chat collector or remote backup. Product ReviewEvent records retain their existing per-change meaning. Missing historical reasoning, effort measurements and human validation are not inferred.

`React UI → same-origin Express API → synchronous domain/store service → native Relate → WAL + Parquet`.

- `src/`: interaction state and rendering. Impact results always come from the native API; the inventory walkthrough identifies seeded items only as navigation/evidence tasks.
- `shared/types.ts`: response types, graph/evidence/change/review contracts.
- `server/app.ts`: HTTP validation, local Host/Origin checks, errors.
- `server/store.ts`: parameterized Cypher, graph traversal, atomic changes, immutable snapshots, reviews.
- `server/ingestion.ts`: validated source versions, evidenced items, dependency candidates, confirmation and generic proposals; all mutations share the store's serialized transaction owner.
- `server/history.ts`: read-only, validated filters and cursor pages over existing native Change, ReviewEvent and replacement relationships.
- `server/changes.ts`: scalar change summaries and validated keyset pages, shared by bootstrap and the saved-change selector.
- `server/sample.ts`: clearly synthetic source versions and expected seed graph; not runtime AI output.
- `scripts/doctor.ts` and `tests/`: disposable DB verification, never a second owner for the live DB.

### Guided inventory walkthrough (2026-11-15)

`SampleWalkthrough` wraps the mounted workspace views, replacing the general workflow map while active. Seven tasks cover preserved source → confirmed link → downstream evidence → explicit apply → persisted decisions → brief → History. It never calls a mutation endpoint: existing Apply and Save controls own writes. Evidence-open observations gate the first three tasks; selected saved change identity, actual pending reviews and a successfully loaded History page gate the others. Opening evidence is an observable interaction, not proof of comprehension. Review decisions still do not imply completed implementation.

Browser storage contains only a versioned status, step, observed task flags and saved change ID, scoped to the runtime database path. Reads/writes are validated and failure-tolerant. No source text or reason is stored there. Reload offers explicit Resume; Back preserves observations, Restart clears guide observations only, and Replay searches up to 20 cursor pages for a matching saved inventory change. Lookup failure/limits never fall through to a new apply. Modified samples without a matching saved change are rejected without resetting data; missing expected paths are explained. Progress is browser/origin-specific, not synchronized or an audit record.

Navigation keeps Documents/review drafts mounted, exposes a return action when the user leaves the task, and focuses the coach or highlighted target without overlays. The mobile tracker and stage navigation have separate sticky offsets. Pause/Finish focus their replacement panel. Source dialog triggers stay focusable during requests. History reports only the current successful page and clears that observation during loading/failure. No dependency, backend query, schema or sample fixture change is required.

1. **Current workspace wins over the old handoff path.** Ripple was initialized in its own empty workspace. The older unrelated repository remains untouched. The public handoff preserves the original requirements with personal PC paths anonymized; the untouched original remains local.
2. **Native Node binding, pinned 1.0.1.** The official npm package and `@relate/relate-win32-x64` ran successfully on this Windows x64 host. No Python fallback, fake DB, external Neo4j service or Rust build was needed.
3. **Single synchronous owner.** Each HTTP handler completes all database calls without `await`. A transaction cannot overlap another handler. An asynchronous store implementation must add an explicit queue covering reads as well as the entire write transaction. Scaling beyond local single-user is not supported.
4. **Data outside OneDrive.** Default storage is LocalAppData/Ripple/demo-v1. Source may remain in OneDrive; the active DB should not. Path override is server-only.
5. **Bounded Cypher paths.** `MATCH p=(dependent)-[:DEPENDS_ON*1..8]->(target)` filters every relationship to confirmed and every path to unique nodes. It excludes the target itself. Native DB paths are grouped by dependent item; all returned paths are retained. A 501st row detects the 500-path cap. A path at depth 8 conservatively indicates possible truncation. Incomplete/missing-evidence previews cannot be applied.
6. **Immutable evidence contract.** SourceVersion is identified by ID/version and SHA-256 of UTF-8 text. Evidence offsets are UTF-16 code units, start-inclusive/end-exclusive; exact slice and hash are checked. The public API has no source-mutation endpoint. Fault-injection tests intentionally corrupt DB data to verify detection. Items and dependencies have distinct evidence links/IDs.
7. **Changes are atomic and idempotent.** UUID requestId + payload fingerprint detects reuse. Within one explicit transaction, lookup prior request, check revision, validate evidence, query the old graph, save Change and Review snapshots, then update body/revision. A failure rolls the whole write back. No automatic retry on a conflicting revision.
8. **Historical context stays readable.** Change stores the pre-change ImpactResult (including immutable source text) as a JSON-serialized Relate property. Review stores its path snapshot plus current status. ReviewEvent nodes preserve each distinct decision update; identical repeated saves do not create events. Keep/revise/defer never deletes dependencies or marks implementation complete.
9. **Read-only interactive graph presentation.** React Flow 12.12.1 supplies pan/zoom/fit and accessible custom node buttons; Dagre 3.1.3 positions the returned nodes. The client never calculates authoritative impacts or edits graph relations. Every path retains its evidence list. Larger graph performance remains unmeasured.
10. **Local server and assets.** API and UI share one loopback origin. Host and Origin checks reject cross-site writes; JSON schema/body limits reject malformed input. No auth or multi-user deployment. Fonts are packaged through Fontsource, with no runtime Google Fonts request. Production uses the same API and compiled static assets.
11. **Astra development configuration, separate from product AI.** The project default is `gpt-6-astra`/high and the launcher passes explicit flags. No secret API key or extra AI service is introduced. Running chat selection is outside config-file control. CLI login checked; no new Astra model invocation was made as part of setup.
12. **Engine lifecycle.** Relate 1.0.1's Node API offers checkpoint but no explicit close method. Shutdown checkpoints and exits. Process-restart tests, not two simultaneous handles, prove reopening. WAL tests exit without an explicit final checkpoint. These are not power-loss/hardware-failure tests.
13. **Public source, local runtime.** The user selected `piecemakerz/Ripple`, an existing public GitHub repository with an MIT license. Preserve its history and license. Commit source, dependency locks and sanitized verification evidence; keep live databases, local backups, credentials and build outputs outside Git. Source publication does not turn the loopback-only server into a hosted demo.
14. **Version-matched official development context.** Use the Node/TypeScript skill and types shipped with the pinned Relate npm package. The launcher and verification gate check their presence and execute a parameterized in-memory read before development. This is separate from the optional upstream CLI skill/agent-context and never opens the live store. The four organizer-linked resources and idea comparisons are recorded in `docs/RELATE_RESOURCES.md`.
15. **Small project skill set.** Four reviewed upstream text snapshots and one Ripple verification skill live under `.agents/skills`. Pin provenance and normalized tree hashes, keep upstream instructions intact, load only relevant references, and adapt React guidance to Vite/Express. `ai:doctor` is part of the completion gate and launcher. CI status uses a token-free public read for the exact committed SHA; optional plugin connection does not block local development. No new agent, model API, global permission policy or hosting service is introduced.

## Data and API

Nodes: Item, Person, SourceVersion, Evidence, Proposal, Change, Review, ReviewEvent, RippleMeta, Mutation. Stable node IDs have unique constraints. Current schema version: 2. Opening a version-1 store performs one explicit transaction to add the Mutation ID constraint and advance metadata; all existing graph, source and review records remain intact. Unknown versions and non-empty unrecognized stores are refused.

## Manual M2 ingestion

- Sources are append-only. New documents get a server UUID and integer version 1; subsequent versions require the current version number. Sample documents with decimal versions cannot be used as import targets. Original text (including uploaded BOM/CRLF), SHA-256 and evidence slices remain immutable.
- The UI accepts UTF-8 `.md`, `.markdown`, `.txt` files up to 80 KB or pasted text. Server validation caps each source at 20,000 UTF-16 code units, 50 source versions, 100 items, 200 dependency records and 100 proposals per workspace. JSON bodies are limited to 256 KB. Limits include sample data and rejected candidates. There is no deletion/reset UI in this slice.
- Users create evidenced items, then proposed `DEPENDS_ON` edges. Candidate revision and both endpoint item revisions are recorded; confirmation revalidates those revisions and the evidence. Rejection remains possible for an outdated candidate. Candidate decisions are terminal. Proposed corrections require rejecting and recreating; confirmed corrections use the replacement operation below. The graph query still follows confirmed edges only.
- Duplicate proposed/confirmed directed pairs and self-dependencies are refused. Cycles across different items remain supported by the existing bounded traversal. These limits do not guarantee bounded query runtime for dense graphs.
- Each ingestion mutation validates input, checks a UUID request receipt and payload fingerprint, and atomically saves data/evidence plus a Mutation receipt. Identical retries return the original response; reuse with different input conflicts. Receipts preserve the manual candidate decision record. All Cypher values are bound.
- Generic proposals preserve the item's expected revision and evidence. They open the existing change/impact/review UI. Applying still recomputes and snapshots current confirmed paths atomically. A stale proposal must be recreated; it cannot silently update a newer item.
- Evidence selection maps textarea-normalized line endings back to the exact original UTF-16 slice. Repeated quotes require explicit occurrence selection (first 100 shown; a longer quote narrows the list). Text/Markdown is rendered as plain text, never executable HTML.
- Dense levels use the read-only Dagre/React Flow canvas described above; the complete path list remains available. Large-workspace performance remains unmeasured.
- No AI extraction, external provider, paid call or collaboration was added. Manual confirmation asserts the user's semantic judgment; the server checks quote integrity, not whether the text logically proves the dependency.

Relationships: DEPENDS_ON, OWNED_BY, EVIDENCED_BY, FROM_SOURCE, CHANGES, FOR_CHANGE, FOR_ITEM, FOR_REVIEW. DEPENDS_ON properties include ID/status/evidenceId/from/to. The authoritative direction is the actual graph edge; rendering derives endpoints from returned paths.

## Confirmed relationship amendments

- `POST /api/dependencies/:id/replacements` accepts a UUID request ID, expected relationship revision, replacement endpoints and their expected item revisions, exact evidence slice and a non-empty reason. It handles both evidence-only amendments and endpoint replacements. Self-links, duplicate active directed pairs, unchanged endpoints/evidence, inactive relationships and stale revisions are refused.
- The existing synchronous transaction owner and Mutation receipt mechanism atomically append new evidence and a confirmed edge, mark the old edge superseded, advance its revision and persist the result. The old edge retains its endpoint/evidence properties. New edges carry `supersedes`, `reason`, `createdAt`; old edges gain `supersededBy`. Retry checks precede revision/state checks, so retries return their original receipt even after later replacements.
- Schema remains 2: these are additive relationship properties with no new node type/constraint. Old sample edges expose revision 1 when the property is absent; their first replacement persists revision 2. Existing manual candidates retain their revisions. Workspace dependencies derive endpoints from the actual graph, while candidates contains only original manual proposals and their lifecycle states.
- No Change, Review, ReviewEvent, SourceVersion or existing Evidence is rewritten. Existing change snapshots remain historical; future impact queries traverse only current confirmed edges. Relationship confirmation is a graph correction and does not increment item revisions or create implementation reviews. A future item change recomputes its impact atomically as before.
- The editor captures endpoint revisions on opening; a workspace refresh does not silently rebase its draft. Conflicts ask users to reopen against current revisions. Identical retries within the page reuse the request ID, including after a lost response/workspace-refresh failure. Drafts remain in memory across panel switches/failures; reloading loses unsaved input. Evidence choice preserves UTF-16 offsets, CRLF and explicit repeated occurrences.
- The 200-record cap includes all superseded generations; history is never pruned to make room. There is no retirement-only action, restore button or automatic semantic evidence verifier. History search is described below. To correct a replacement again, create another generation and provide its reason.

## Item history

- `GET /api/history` uses the existing backend connection and three bounded, parameterized Relate projections: applied Change nodes; ReviewEvent → Review → Change/Item; and paired DEPENDS_ON generations linked by `supersedes`/`supersededBy`. No new schema, event copies or historical writes. It does not infer impact from the current graph.
- Changes match their target plus the originally impacted item IDs from their saved Review records. Reviews match the reviewed item and the changed item; relationship events match both old and new endpoints, deduplicated in the response. A change with no impacts still appears. Pending reviews and identical repeated saves do not invent events. Each replacement generation remains an event even after another replacement.
- Optional filters: `itemId`, `kind` (change/review/relationship), `status` (keep/revise/defer), case-insensitive literal substring `q` (up to 200 characters), `from` and `until` (UTC ISO timestamps with milliseconds). Status selects historical ReviewEvent status, not the latest Review status. Search includes IDs, associated item titles, changed text and reasons, not source-document contents. The UI converts inclusive local calendar dates into the API's half-open `[from, until)` range.
- Filters precede query limits. Each selected kind reads at most `limit + 1` summaries (default 25, maximum 50), sorted by timestamp then prefixed event ID descending. The merged page uses the same ordering; a base64url cursor carries that tuple. Equal-millisecond events are deterministic, not assigned an invented intra-millisecond chronology. Newer events do not shift subsequent pages; Refresh returns to the first page. There is no total-count claim or silent history cutoff.
- Summary responses omit saved path/source snapshots. Opening a change loads its existing saved detail; opening a review selects its item and displays the latest review plus the original paths. Exact evidence is loaded on demand through the existing validated evidence API. Abortable requests prevent obsolete filter responses from replacing newer ones; failures expose a retry and preserve filters. Forms, results, empty states and previous/next navigation work at 390px.
- Filters and current page survive view switches only; reload resets them. No export, persisted filter URL, pending-review work queue or source-content search is included. Query result bounds do not bound engine scan/sort time. Workspace bootstrap now uses the change summaries described below; this is not a claim of whole-app large-history scalability.

## Bounded change loading

- `GET /api/workspace` replaces the old `changes: Change[]` field with `changePage: { entries, nextCursor, pageSize }`. It returns the newest 25 summaries containing only ID, target item ID, before/after revision and timestamp. `GET /api/changes` returns the same page shape; `limit` accepts a single decimal integer from 1 to 50 (default 25). Unknown/repeated parameters, malformed cursors and invalid page sizes are rejected. Client and server must be updated together; this local MVP has no versioned external API contract.
- Relate projects scalar properties directly, never returning complete Change nodes or decoding their snapshots for the list. A bound `limit + 1` detects another page. Ordering is `createdAt DESC, id DESC`; the validated base64url cursor contains that tuple. Equal timestamps are deterministic. New records above a cursor do not move the remaining results; Refresh returns to the first page. No records are deleted or migrated; schema stays at version 2.
- The selector reuses the bootstrap page and fetches subsequent pages only when requested. Selecting a change, including one reached from History outside the current page, fetches its original `GET /api/changes/:id` detail. The selected option remains available when paging. Paging and refreshing the list do not change the selected detail or review drafts. Failed list requests expose a local retry; detail Reload retains the requested change instead of silently selecting the newest. Abort controllers prevent obsolete reads from replacing current results.
- Reloading the browser still opens the newest saved change and resets page navigation; unsaved drafts remain memory-only. The selector keeps one summary page plus an optional selected entry, and a cursor stack for Previous navigation. Sources/items/proposals still load within existing ingestion caps. A selected change still returns its full path/source snapshot and review history; history scan/sort cost, a single large detail and dense traversal remain separate scalability limits.
- A controlled synthetic 55-change production fixture measured 6,950 UTF-8 JSON bytes for workspace versus 459,491 bytes for the equivalent old all-snapshot response (98.5% less). The 25-entry change page was 3,605 bytes. This measures the bootstrap response only, not total page traffic, latency, engine memory, real-document accuracy or maximum capacity. Browser network inspection confirmed bootstrap plus exactly one selected-change detail request. See QA for the method and checks.

### Remaining product limits

- Store APIs are synchronous and can block the event loop on larger graphs. The depth/row cap is an output bound, not a strict query execution-time/memory bound. M2 should set domain ingestion limits before accepting arbitrary large input.
- Built-in and manually created change proposals are selectable. Imported items can be both the changed item and impacted items.
- Review updates use last-write-wins within the single-user app. Multi-tab conflicting review drafts are not revision-checked yet. Change requests are revision-checked.
- Review and document drafts survive panel switches and failed requests only in the current browser page. Reloading loses unsaved input; saved source versions, candidates, proposals and reviews persist.
- Raw direct access to Relate can bypass application invariants. Only the backend should write the live store.
- A separate SemVer submission archive was generated from disposable data after its writer exited; copied-store and extracted-archive reopening passed. Its 17 file hashes, fixture identity and runtime source commit accompany the local package. It does not export the user's live store and has no public download yet. Archive publication, the recorded demo and final submission remain M4 work; public application hosting is not configured.
