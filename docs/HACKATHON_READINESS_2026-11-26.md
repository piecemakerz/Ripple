# Ripple 수상 경쟁력과 제출 준비 평가

같은 날의 후속 [비판적 재검토](HACKATHON_CRITICAL_REVIEW_2026-11-26.md)가 수상 충분성 판단을 보완한다. 아래 기술·재현 결과는 유지하지만, 후속 검토는 공개 유사 출품작, 준비 비용, 의미 범위, 오래된 검토 저장과 영상 첫 장면의 약점을 추가했다. 이 문서를 상위권 확보나 최종 제출 완료로 해석하지 않는다.

확인일: **2026-11-26 KST**. 대상은 공개 HEAD `e7d28a7` 위의 현재 로컬 구현이다. 공식 요건은 온라인으로 다시 확인했고, 판단의 근거는 코드·실제 native Relate 검사·이번 브라우저 실행이다. 다른 출품작의 내부 구현이나 심사 점수는 확인하지 않았다.

**판정: 기술과 핵심 사용 흐름은 경쟁력 있는 MVP다. 현재 증거만으로 수상하기에 충분하다고 단정할 수 없으며, 공개 제출 상태는 아직 미완료다.** 가장 큰 공백은 기능의 수가 아니라 최신 구현의 전달, 필수 공개 데모, 실제 사용 가치의 관측이다. 화면·테스트 통과를 독립 사용자 검증으로 계산하지 않는다.

## 이번에 구현한 개선

1. **사례로 바로 진입:** SemVer 실행 명령이 정확한 proposal/item URL을 출력한다. 적용 후 saved change/item URL로 바뀌며 새로고침·재시작 후 같은 검토를 연다. 재고 예제도 같은 선택 상태를 사용한다. 잘못된 링크에는 영어/한국어 안내가 표시된다.
2. **재현 가능한 영구 DB 자료:** 사용자 DB와 무관한 fixture를 생성하고 작성 프로세스 종료 후 고정한다. 5개 항목·7개 경로·6개 근거·저장된 Defer 기록을 읽기 전용 복사본에서 확인한다. 파일 변경·누락·추가를 해시로 거부한다. 실행은 별도 쓰기 가능한 복사본에서 한다.
3. **현재 코드의 식별:** 제출 묶음에 현재 소스, 라이선스, fixture, 설치 안내, 파일 해시와 Git dirty 상태를 포함한다. 예전 CI가 현재 미커밋 코드를 검증했다고 표시하지 않는다.
4. **심사 설명 정리:** 오래된 배점·실행 안내를 바로잡고, 실제 검토 화면·실패 재시도·다중 경로·모바일 원문을 확보했다. 인간 성과를 추정해 넣지 않는다.

## 실제 검증과 한계

- **자동 검사:** 최종 `npm run verify` 84/84 통과, 실패/스킵 0. 포맷·엄격 타입·고정 스킬·native context·실제 DB 통합·production build 통과. 최초 선택상태 통합에서 남은 setter 1곳으로 타입 검사가 실패했으며 수정 후 gate를 다시 통과했다.
- **새 설치:** 일반 재현 명령과 실제 심사용 묶음의 별도 복사본에서 `npm ci`, 전체 gate 84/84와 `doctor` 통과. 묶음의 읽기 전용 검사와 별도 쓰기 복사본의 실제 브라우저 실행도 통과. [STATUS](STATUS.md)에 버전 구분과 로그를 기록했다.
- **브라우저:** SemVer 직접 진입, 두 경로, 원문 [177,255), 5개 검토/7개 보존 경로, 모든 결정 유형, 실패 후 입력 유지와 재시도, 같은 링크로 선택·이유·5/5 복원, History 6개 이벤트. 재고 예제는 정확히 D1/D2/T1/T2 영향. 실제 390×844 CSS px에서 한국어 UI·영어 원문·저장된 이유와 가로 넘침 없음 확인.
- **도구 한계:** 다운로드 이벤트 대기가 시간 초과되어 이번 브라우저 다운로드 완료는 주장하지 않는다. 원문 및 요약 생성의 기존 native 회귀 검사는 통과했다. 390 기기 설정을 먼저 110% 브라우저 줌에 적용했을 때 실제 CSS 폭은 355였고, 보정 후 실제 390을 측정했다. 물리 기기·새 인간 테스트·추가 스크린리더 검사는 수행하지 않았다.
- **증거의 뜻:** 고정 문서 사례와 합성 검토 이유다. 자동 추출 정확도·일반 사용자 성과·완전한 WCAG 준수·임의 규모의 성능을 입증하지 않는다. 외부 배포·공개 업로드·접수 여부는 별개다.

## 다음 순서

**P0 — 제출을 막는 공백:** 최종 소스 공개·해당 커밋 CI → 검증한 영상/DB 자료 공개와 로그인 없는 접근 확인 → 참가자 사실·설명 검토 → Devpost 접수 및 실제 제출본 동결. 묶음이 있다는 사실만으로 제출 완료가 되지는 않는다.

**P1 — 수상 경쟁력 증거:** 처음 보는 대상 사용자 2–3명에게 본인의 공개 가능한 변경 사례를 준비부터 판단까지 수행하게 한다. 도움 횟수, 관계 준비 시간, 누락·오탐과 근거 설명, 현재 방식으로 돌아갈 이유를 관측한다. 전원에게 답을 미리 알려주거나 AI 역할극을 독립 사용자로 세지 않는다. [X05–X09 프로토콜](learning/EXPERIMENTS.md)

**P2 — 관측 후 제품 개선:** 준비 비용이 크면 입력 단순화/검토 가능한 후보 생성, 재방문 손실이 크면 초안 복구, 다중 탭 충돌이 관측되면 검토 리비전 검사를 우선한다. 대규모 성능·운영체제 확대는 재현 수요에 맞춰 측정한다. 지금 근거 없이 기능 수를 늘리는 것은 수상 증거의 공백을 메우지 못한다.
